动工前的 60 秒自检

在把它当成日常工具之前，先花一分钟确认三件事：它确实装好了、文件都在该在的地方、以及哪些规矩碰了会出问题。这三步能挡掉后面大半的「怎么又不灵了」。

先认清：谁在管什么文件

官方文档 · 配置与文件布局

Hermes 把「设置」「密钥」「身份」「项目规则」「学到的东西」拆在不同文件里，各有明确归属。弄混了是最常见的一类错误。

文件 / 目录放什么谁写它
config.yaml所有行为设置：模型、终端后端、显示、审批、语音……你，通过 hermes config set（别手改）
.env只放密钥：API key、token你。行为配置写进这里就是错的
SOUL.md它的身份与语气（全局，与项目无关）你
MEMORY.md / USER.md它记住的事实 / 关于你的画像它自己（可加审批闸门）
AGENTS.md、.hermes.md、CLAUDE.md项目规则，放在项目目录里你；每次会话自动注入
skills/可复用的操作流程（它会自己攒）你 + 它
state.db全部会话与消息（SQLite + FTS5 检索）运行时
sessions/ · logs/网关路由索引、轨迹 JSONL / 运行日志运行时
auth.jsonOAuth 令牌与凭据池登录流程
profiles/<名>/另一套完整的上面这些（多实例隔离）hermes profile
两条硬规矩

① 密钥进 .env，设置进 config.yaml——把 TERMINAL_ENV=docker 这类行为开关塞进 .env 是错的。② 不要手改 config.yaml，用 hermes config set KEY VAL；一个多余缩进就能让正在跑的网关报废。

两条不能碰的规矩

仓库 AGENTS.md · 架构不变量

这两条不写在 --help 里，但它决定了 Hermes 一切设计。你自己二次开发时，踩这两条会得到「看起来能用、实际上很贵」或「偶发串号」这类最难查的 bug。

规矩说人话踩了会怎样
按会话的 prompt 缓存是神圣的 一次会话里，系统提示、历史消息、工具集必须保持字节稳定；唯一允许的上下文改写是压缩。任何想中途「注入」的东西只能走用户消息或工具结果。 缓存前缀失效 → 每一轮都按全价重读整段对话，账单翻好几倍；换成中途改系统提示让功能「生效」的直觉做法，在这里等于写了 bug。
一个进程服务多个 profile 跑在「回合之外」的代码（启动探测、定时器、延迟回调、RPC、线程跳转、子进程）都必须显式绑定所属 profile；os.environ 和模块全局拿到的是启动 profile 的值。 静默的「默认 profile 泄漏」——另一个实例读到你的配置、写出你的会话，这是这个项目里出现频率最高的 bug 类型。
对应的自查命令

hermes prompt-size 会把系统提示 + 全部工具 schema 的字节占用按块列出来（--json 给机器读）。想看「到底是什么在吃掉我的上下文」，这是最直接的一把尺子。

3 · 目录、文件与 profile

官方文档 · 多实例与文件布局

默认一切都在 ~/.hermes。用 profile 就能在一个进程里同时服务多个互不干扰的实例——每个 profile 有自己的配置、会话、技能、记忆、凭据。

profile 常用动作

hermes profile list # 现有实例 hermes profile create work --clone # 克隆当前配置建一个新实例 hermes profile create work --clone-all # 连会话/技能/记忆一起克隆 hermes profile use work # 切换默认 hermes profile show # 当前实例信息（含真实 HERMES_HOME） hermes --profile work # 单次调用临时用某个实例（-p） hermes profile export work > work.tar # 导出分发 hermes profile import work.tar # 导入 hermes profile rename old new · hermes profile alias NAME · hermes profile delete NAME
写脚本时注意

profile 激活后 ~/.hermes 不是真实路径。要解析真实目录，读环境变量 HERMES_HOME，不要硬写 ~/.hermes。这在仓库里是 lint 级别的硬规则（get_hermes_home() 对应 display_hermes_home()）。

二分法排查顺序

先 hermes --safe-mode 跑一遍——如果问题消失了，就是你自己的配置/插件/规则；还在，就是 Hermes 本身或环境。再 hermes --ignore-rules（跳过 AGENTS.md / SOUL.md / 记忆 / 技能注入 + 用户配置 + 插件 + MCP）缩小范围。这两条比逐个关东西快得多。

问题二

命令行怎么用

Hermes 的入口是一个 hermes 命令：不带子命令就是聊天，带子命令就是工具。真正拉开效率差距的不是背命令，而是三件事——用对启动方式、用对输入手法、看懂屏幕上在说什么。

1 · 四种启动方式

实测 · hermes --help 与 hermes chat --help
方式命令输出行为用在哪
交互式 hermes

hermes --cli		 横幅 + 提示符，多轮对话 日常。默认是经典 REPL；display.interface: tui 或 --tui 切到 Ink TUI，--cli 强行退回经典
单次提问 hermes chat -q "问题" 问完打印回复并退出；-Q 再压掉横幅、转圈与工具预览 临时问一句、写在脚本里
纯管道单发 hermes -z "问题" stdout 只有最终回答文本——没有横幅、没有转圈、没有工具预览、没有 session_id 行；审批自动放行 喂给别的程序的管道 / CI。工具、记忆、规则和当前目录的 AGENTS.md 照常加载

管道里想知道花了多少钱

-z 配 --usage-file 路径，会在跑完后把一份 JSON 用量报告写到指定文件（估算花费、token 数、模型、api_calls）。即使这次跑失败了也会写，所以流水线永远能记账。该参数只在 -z/--oneshot 下有效。

管道单发 + 记账 + 预载技能

hermes -z "把 /var/log/app.log 里今天的报错归类成一张表" --usage-file /tmp/usage.json hermes chat -s github-pr-workflow -q "开一个草稿 PR" cat prompt.txt | hermes chat --query-file - # 提问原文不被 shell 改动

--dev配 --tui：直接跑 TS 源码，跳过构建改 TUI 的人用
-p, --profile NAME 隐藏本次命令用哪个 profile不在 hermes --help 里列出，但在预解析阶段就生效（早于任何模块导入，所以 HERMES_HOME 会被正确改写）。写法：hermes -p work status
--config PATH 隐藏指定配置文件路径同样只出现在更新器的保留参数表里，不在主帮助中
顺序有讲究

-p、--config 是在 argparse 之前被「预解析」摘掉的，所以它们必须放在子命令之前：hermes -p work status 对，hermes status -p work 可能不被识别。

6 · @ 引用：把现场塞进一句话

官方文档 · Context References

在输入框里打 @ 再接一个引用，Hermes 会把它展开并追加到消息末尾的 --- Attached Context --- 段里。这是 CLI 独有的能力，网关平台不会展开。

写法注入什么
@file:path/to/file.py文件全文
@file:path/to/file.py:10-25指定行范围（从 1 开始，含两端）。写单行就 :42。范围不合法就静默退回全文
@folder:path/to/dir目录树 + 文件元信息（最多 200 项，超出用 - ... 省略）
@diffgit diff（未暂存的工作区改动）
@stagedgit diff --staged（已暂存）
@git:5最近 N 个提交（含补丁），N 上限 10
@url:https://…抓取网页正文并注入

多条可以混用：看一下 @file:main.py，顺便看看 @file:test.py。引用值末尾的逗号、句号、分号、感叹号、问号会被自动剥掉。

安全阈值取值行为
软上限上下文的 25%追加一条警告，照常展开
硬上限上下文的 50%拒绝展开，原消息原样返回
敏感路径见下直接拒绝并给警告
工作区之外—拒绝（所有路径都按当前工作目录解析）
被永久封锁的路径

单个文件：~/.ssh/id_rsa、~/.ssh/id_ed25519、~/.ssh/authorized_keys、~/.ssh/config、~/.bashrc、~/.zshrc、~/.profile、~/.bash_profile、~/.zprofile、~/.netrc、~/.pgpass、~/.npmrc、~/.pypirc、$HERMES_HOME/.env。
整个目录：~/.ssh/、~/.aws/、~/.gnupg/、~/.kube/、$HERMES_HOME/skills/.hub/。
二进制文件按 MIME 与空字节扫描识别，会被拒绝（已知文本扩展名例外）。

别拿它当搬运大文件

@file: 注入的内容会算进上下文；会话被压缩时，这些内容是被摘要而不是原样保留。大文件请用行范围 @file:main.py:100-200 只取相关段落。

四个高频用法

# 代码审查：只看改动 审一下 @diff，重点找安全问题 # 带上下文调试：测试和实现一起给 这个测试挂了。测试是 @file:tests/test_auth.py，实现是 @file:src/auth.py:50-80 # 接手陌生项目 这个项目是干什么的？@folder:src @file:README.md # 对比阅读 比较 @url:https://arxiv.org/abs/2301.00001 和 @url:https://arxiv.org/abs/2301.00002 的做法

6 · 自定义命令与 bundles

仓库 · hermes_cli/AGENTS.md 与 skills 机制

斜杠命令表面上是一张固定清单，实际上是可扩展的——这是最容易被人忽略的一点。

  • 每个技能就是一条斜杠命令。 技能装好之后，技能名直接当命令用：/github-pr-workflow、/arxiv。它是把技能内容作为一条用户消息注入，不是改写系统提示——这样才不会破坏缓存。
  • bundles 是别名。 一个 bundle 名字可以一次载入好几个技能，适合「我每次都要同时用这三样」的场景。CLI 侧是 hermes bundles，会话内是 /bundles。
  • 插件和供应商可以带来新子命令。 例如 hermes photon setup 这类命令，只有装了对应插件才会出现在 --help 里。
  • 改系统提示状态的命令默认「延迟生效」。 它们不会当场改运行中的提示，而是排到下一次会话；想立刻生效，加 --now（例如 /skills install xxx --now）。这条规则是为了保护 prompt 缓存，在根 AGENTS.md 里是硬约束。

config.yaml 里的两种写法

# 完整式：别名自带 provider 与端点 model_aliases: fav: model: claude-sonnet-4.6 provider: anthropic local-qwen: model: qwen3.5:397b provider: custom base_url: "https://ollama.com/v1" theta: model: theta-1 provider: custom base_url: "https://theta.example.com/v1" key_env: THETA_API_KEY # 或 api_key: "\${THETA_API_KEY}" # 简写式："供应商/模型"，也可以直接用命令加 model: aliases: fav: openrouter/anthropic/claude-sonnet-4.6

带 base_url 的别名，密钥不继承

5 · 省钱：缓存、压缩与本地模型

官方文档 · Tips / 仓库 AGENTS.md 不变量

Hermes 的花费大头不是「输出多少字」，而是「同一段前缀被重复按全价读了多少遍」。理解下面四点，账单能差好几倍。

机制怎么运作你要做什么
前缀缓存 系统提示 + 历史是稳定的前缀，供应商会缓存它，后续消息命中缓存就便宜很多 一次会话里别频繁换模型 / 别触发 fallback / 别转凭据池——这三件事都会让下一轮把整段对话按全价重读。偶尔换没事，长会话里频繁换就是乘法级涨价
上下文压缩 会话快满时自动压缩（会话卫生阈值 85%、agent 侧 50%），把它换成摘要。状态栏 cmp N 是压缩次数 配置在 compression.*：threshold（默认 0.50）、target_ratio（默认 0.20）。想手动压用 /compress here 10 保留最近 10 轮
侧路小模型 起标题、压缩、嵌入、检索、看图这些杂活都走 agent/auxiliary_client.py，可以逐个任务单独钉模型 在 config.yaml 的 auxiliary: 段下把杂活指到便宜模型，主模型只干正事
本地模型 任何 OpenAI 兼容端点都能接（Ollama / llama.cpp / MLX） 零 API 成本，代价是速度与能力。适合跑批、跑简单的、或者敏感数据不出本机
查账的三个入口

/usage 看本次会话与限流；hermes insights --days 30 --source cli 看 30 天用量分析（--source 可按平台过滤）；hermes -z "…" --usage-file out.json 给单次脚本调用留一份机器可读的账。想看「上下文到底被谁吃掉了」，用 hermes prompt-size --json。

还有一层省钱开关：provider routing

走 OpenRouter 时，可以在配置里指定 provider 偏好（省钱 / 快 / 质量优先），官方文档的「Provider Routing」一节有完整键名。同一批模型不同路由的价格能差不少。

问题五

记忆、技能与自我改进

Hermes 自称 self-improving，靠的是三套东西：上下文文件（你告诉它的规则）、记忆（它记住的事实）、技能（它学会的流程）。三者用途不同、写入者不同、加载时机也不同——混用是「为什么它记不住」的头号原因。

1 · 上下文文件：AGENTS.md 一族

官方文档 · Context Files

发现顺序是先匹配先赢——一次会话只加载一个项目上下文来源。这一点很多人不知道，于是出现「我明明写了 AGENTS.md 但它没读」的情况（其实是被更高优先级的 .hermes.md 顶掉了）。

文件（按优先级）怎么被发现什么时候用它
.hermes.md / HERMES.md 向上遍历父目录，一直走到 git 根为止 要层次化的项目规则（根目录一套 + 子包各自覆盖），或者要让规则从上层目录继承
AGENTS.md / agents.md 只看当前目录——子目录和父目录的副本都被忽略 同一个项目还要给别的 agent（Claude Code、Codex、OpenCode）用。「只看当前目录」这个契约保证了文件可移植
CLAUDE.md / claude.md 只看当前目录 同上，Claude 风格
.cursorrules / .cursor/rules/*.mdc 只看当前目录 从 Cursor 迁过来的，不用重复写一份
限制值后果
单文件长度上限20,000 字符超了做头 + 尾截断，中间被丢弃并留 [...truncated...] 标记
注入频率每一条消息每个字符都算 token，所以要精简；规则多了拆成技能而不是堆一个文件
安全扫描注入前过威胁模式扫描器命中提示注入 / promptware 的片段被替换成 [BLOCKED: ...] 占位。被拦的是片段不是文件，其余内容照常加载
子目录的 AGENTS.md 不是不生效

根/当前目录的顶层文件在会话开始时注入。子目录里的 AGENTS.md 是在工具调用过程中被惰性发现的（走 subdirectory_hints.py），注入到工具结果里，不占系统提示。所以「子目录规则在它读到那个文件时才出现」是设计，不是 bug。

别把项目规则放到 home 目录

把规则写在 ~/.hermes/AGENTS.md 里，只有当 Hermes 恰好在该目录下运行时才会加载，别的项目一概读不到。要跨项目生效：改用 $HERMES_HOME/SOUL.md（只管身份与语气），或把流程做成技能装起来。

2 · SOUL.md：它是谁

官方文档 · Personality & SOUL.md

SOUL.md 放在 $HERMES_HOME 下，只要存在就总是加载，和项目上下文文件互相独立。它定的是「这个 agent 是谁」——默认语气、工作风格、价值观，而不是项目规则。

SOUL.md 的一个最小例子

# Soul 你是一名资深后端工程师。说话简短直接，不要开场白和总结。 除非被问到，不要解释你打算怎么做，直接做。 优先给最小改动，而不是看起来更漂亮的重写。 永远考虑错误处理和边界情况。

两种人格切换手段：全局 —— 编辑 SOUL.md（持久，所有会话生效）；会话内 —— /personality [名字]（临时，可切回）。内置了一批现成人格，也可以自定义 persona 定义。

3 · 记忆：它记得什么

官方文档 · Memory · 官方文档 · Memory Providers

记忆是「事实」：你的环境、偏好、项目位置、它从你身上学到的习惯。记忆 ≠ 技能——记忆管「是什么」，技能管「怎么做」。

文件内容容量上限
MEMORY.md它的工作笔记：环境事实、约定、踩过的坑约 2,200 字符
USER.md关于你：身份、角色、偏好、风格约 1,375 字符
最重要的一条：记忆是「快照」

记忆在会话开始时被读进系统提示，然后整场会话不再变。它在会话中写的改动会立刻落盘，但不会出现在当前会话的系统提示里——要等下一次会话才看到。这是为了不破坏 prompt 缓存，属于刻意设计。
所以你让它「记住这个」，它是真记住了，只是这一轮里它自己看不见。

记忆的开关与外部记忆后端

hermes memory setup # 配置外部记忆 provider hermes memory status # 当前用的是哪个后端 hermes memory off # 关掉 hermes memory reset # 重置 # config.yaml 里的相关键 # memory: # memory_enabled: true # user_profile_enabled: true # provider: ... # write_approval: true # 写入前要你批准

外部记忆后端以插件形式提供，官方列出的包括 Honcho、OpenViking、Mem0、Hindsight、Holographic、RetainDB、ByteRover、Supermemory。什么都不配就用内置的文件式记忆。

记忆满了怎么办

它有硬上限，满了会自己合并条目。你也可以直接指挥它：「清理一下记忆」「把那条 Python 3.9 的笔记换成 3.12」。会话内用 /memory pending 审阅待写队列，/memory approve / /memory reject 放行或驳回（开了 write_approval 才需要）。

4 · 技能：它会什么

官方文档 · Skills · Curator · 仓库 skills/AGENTS.md

技能是「流程」：一份按需加载的知识文档，讲清一个多步骤任务该怎么做。渐进式加载——平时只有技能名和一句描述占上下文，真正用到时才把全文读进来。

来源说明命令

三个和技能有关的隐藏机制
  • 技能即斜杠命令。 装好后 /技能名 直接调用，内容作为一条用户消息注入（不是系统提示）。
  • 技能可以跨设备同步。 hermes sync 是 Skill Sync——把你自己的技能在多台机器和团队之间同步。
  • 技能包 bundles。 一个名字载入多个技能，适合固定搭配。

Curator：技能的自动维护

后台有个维护进程（curator）在管它自己创建的技能：追使用次数、把闲置的标记为过时、把过时的归档，并在动手前留一份 tar.gz 备份。

关键事实说明

问题六

Hermes 的能力边界由两件事决定：工具集（给它哪些能力）和审批（它动手前要不要问你）。这一节还讲命令到底在哪台机器上跑——这一条决定了「安全」在你这台机器上是真安全还是纸面安全。

1 · 工具集：给不给它这个能力

仓库 · toolsets.py TOOLSETS · 官方文档 · Tools

1 · 定时任务 cron

官方文档 · Cron · 仓库 cron/AGENTS.md

一个持久调度器（cron/jobs.py + cron/scheduler.py）。三个入口都能驱动它：cronjob 工具（对话里让它自己排）、hermes cron 命令行、/cron 斜杠命令。

调度写法例子
时长30m、2h、1d
自然语言「每…」every monday 9am、every 2h
标准 cron 五段0 9 * * *
ISO 时间戳一次性在某个绝对时刻执行

作业管理

hermes cron list # 列出作业 hermes cron create "0 9 * * *" # 新建（也接受 '30m' / 'every 2h' / ISO 时间） hermes cron edit ID # 改 hermes cron pause ID / resume ID hermes cron run ID # 立刻跑一次（不等到点） hermes cron remove ID hermes cron status # 调度器状态 hermes cron --accept-hooks list # 无 TTY 时自动批准没见过的 shell 钩子
每个作业可配的旋钮作用
skills给这个作业挂一个或多个技能
model / provider单独覆盖模型（便宜活走便宜模型）
script跑前先采集数据；配 no_agent=True 时脚本本身就是整个作业——完全不过 LLM，只把 stdout 投递出去
context_from把作业 A 的输出链接成作业 B 的输入（串流水线）
workdir在指定目录下跑，并加载该目录的 AGENTS.md / CLAUDE.md
多平台投递结果直接发到指定的消息平台
「纯脚本」型 cron 是最省钱的自动化

经典看门狗场景（磁盘告警、内存告警、CI ping、定期健康检查）用 no_agent=True + script：零 token，脚本 stdout 直接投递到你的聊天平台。文档里的「Script-Only Cron Jobs (No LLM)」一节有完整例子。

cron 的四条不变量
  • 每次运行 3 分钟硬中断。 长任务要么拆开，要么交给别的机制
  • .tick.lock 防止重复 tick。 多个进程共用一份作业库时只跑一个
  • cron 会话默认 skip_memory=True。 定时任务不会污染你的记忆
  • 投递是「加头尾的独立消息」，不镜像进目标会话。 这样才不破坏消息角色交替（role alternation）

2 · 子代理 delegate

官方文档 · Delegation

子代理 = 上下文隔离 + 独立终端会话的子智能体。适合「这活会污染我的上下文」或「这几件互不依赖，并行做」。

用法形态
单个delegate_task(goal=…, context=…)
批量并行delegate_task(tasks=[{…},{…}])，并发上限 delegation.max_concurrent_children（默认 10）
后台delegate_task(background=true) 立刻拿到句柄，父循环继续；子代理完成后结果作为新一轮消息回来
角色leaf（默认，不能再往下派）vs orchestrator（可以自己再派工人，受 delegation.max_spawn_depth（默认 1）约束）
相关配置键（delegation.*）默认说明
max_concurrent_children10一次批量派发的并发子代理上限
max_iterations250每个子代理自己的工具迭代预算
max_spawn_depth1orchestrator 能再往下派的层数
oneshot_max_children2-z 单发模式下的子代理上限（更保守）
orchestrator_enabledtrue是否允许 orchestrator 角色
child_timeout_seconds0（不设）单个子代理的墙钟超时
模型可以不一样

delegation.model / delegation.provider 可以为子代理单独指定更便宜或更快的模型——批量做机械活时这一条省钱很明显。independent_completions 让子代理不继承父对话。

子代理不持久

后台子代理仍然是进程内的：父进程一退出，子代理就丢了。要活过进程重启，用 cron，或者 terminal(background=True, notify_on_complete=True)。

「delegate_task 被限制到 N 个」这种报告

Hermes 里确实有三条真实的并发上限路径，但很多情况下是模型在自我设限、然后用「运行时限制」来合理化。诊断顺序见官方仓库的并发诊断说明：先确认是哪条上限真的触发了。

3 · 会话内的循环：/loop 与 /heartbeat

官方文档 · Recurring Loops / Session Heartbeats

这两个都很容易被误当成 cron。区别在于：它们活在当前这条会话里，用当前这条会话的上下文。

/heartbeathermes cron
在哪跑当前这段对话——完整上下文，记得你们聊过什么每次 tick 开一个全新的隔离会话
进程重启后状态存进 SessionDB，网关会看着它自动恢复完全持久，本来就与进程无关
能有几个每个会话一个不限
适合「我们干活的时候你顺手盯着 X」固定作业、日报、看门狗、投递

heartbeat 的全部用法（别名 /hb）

/heartbeat every 10m 检查部署，有实质变化就报 /heartbeat # 或 /heartbeat status：看间隔与下次触发时间 /heartbeat pause # 停触发但不清除 /heartbeat resume # 恢复（会重新锚定计时器，不会立刻补发一次过期的） /heartbeat clear # 移除 # 间隔最小 60 秒，支持 90s / 10m / 2h / 1d

loop 的两种节奏（别名 /proactive）

# 固定间隔：你给时钟。适合被观察的东西自己有节奏 /loop 5m 看部署状态，上线了就告诉我 /loop 10m /recap # 也可以循环一个斜杠命令 # 自定节奏：它给时钟。不给间隔时，从下限（默认 1 分钟）起步， # 回复没变化就指数退避 2m→4m→8m（上限默认 15 分钟）； # 一旦发现变化立刻回到下限。变化检测是本地摘要比对（忽略时间戳），空闲等待不额外花钱 /loop 盯着这次迁移，有进展就汇报
三者的选择口诀

需要对话上下文 → /heartbeat。需要「做这件事直到达成」 → /goal。需要「每隔一会儿再做一遍」 → /loop。要无人值守、要活过终端关闭 → cron。

5 · 多人多机：kanban 与 peer

官方文档 · Kanban · 实测 hermes kanban / peer

kanban 是一个持久化在 SQLite 里的工作队列，用来协调多个 profile / 多个 worker。用户这边用 hermes kanban <动词>；被派发出来的 worker 会看到一个受 HERMES_KANBAN_TASK 限定的 kanban_* 工具集，普通会话里完全没有 kanban 工具 schema 的占用。

看板常用动词

机制说明
派发器在哪默认跑在网关进程里（kanban.dispatch_in_gateway: true）：回收过期认领、把就绪任务提升、原子认领、拉起被指派的 profile
失败保护连续拉起失败达 failure_limit 次（默认 2）自动 block 该任务；可按任务设 max_retries
隔离边界板是硬边界（worker 的环境里钉死 HERMES_KANBAN_BOARD）；tenant 是软命名空间，用来隔离工作路径与记忆键
多网关部署一块板可以横跨多个按 profile 拆的网关：单一派发器、各 profile 各自投递

peer 是另一条线：跨机器的 bot 与 bot 之间互相私信（peer Hermes 网关）。

2 · MCP 服务器

官方文档 · MCP · 仓库 tools/mcp_tool*.py

Hermes 内置 MCP 客户端：启动时连上 MCP 服务器、发现它们的工具、注册成一等公民工具，和内置工具并排出现。

config.yaml 里的 mcp_servers

mcp_servers: time: # 名字 → 配置 command: "uvx" # stdio 传输 args: ["mcp-server-time"] github: command: "npx" args: ["-y", "@modelcontextprotocol/server-github"] env: GITHUB_PERSONAL_ACCESS_TOKEN: "ghp_..." # 只显式给这一个，其余环境变量不透传 timeout: 60 # 单次工具调用超时，默认 120 connect_timeout: 60 # 首连超时，默认 60 company_api: url: "https://mcp.example.com/mcp" # HTTP / StreamableHTTP 传输 headers: Authorization: "Bearer sk-..." sampling: enabled: true # 允许服务器反过来请求 LLM（默认开）
要点细节
工具命名mcp_{服务器名}_{工具名}，连字符和点会换成下划线（为了兼容 LLM API）。例如 mcp_github_list_issues
环境变量过滤stdio 子进程不会继承你完整的 shell 环境——只有 PATH HOME USER LANG LC_ALL TERM SHELL TMPDIR 和 XDG_*。其余（API key、token）必须显式写在 env 里。这是防止把凭据泄露给不可信 MCP 服务器
错误信息脱敏MCP 工具调用失败时，错误信息里的凭据类模式（GitHub PAT、sk-、Bearer token、token=/password=/secret=）会被替换后再给模型
自动注入发现到的 MCP 工具会自动注入到所有 hermes 平台工具集，每个会话都能用
重连连接掉线会指数退避重连，最多 5 次（1s→2s→4s→8s→16s，上限 60s）
热更新没有热重载：加删服务器要重启 agent。但会话内可以用 /reload-mcp 重载
依赖需要 Python 的 mcp 包（pip install mcp），否则 MCP 支持静默关闭；HTTP 传输还需要该版本带 mcp.client.streamable_http

命令行侧：加、测、逛、反过来当服务器

hermes mcp add 名字 --url https://… # 或 --command "npx …" hermes mcp list hermes mcp test 名字 # 验证连通与工具发现 hermes mcp configure 名字 # 逐个开关工具（挑哪些暴露给模型） hermes mcp catalog # 官方精选目录 hermes mcp install 名字 # 从目录一键装 hermes mcp serve # 把 Hermes 自己变成一个 MCP 服务器 hermes mcp --accept-hooks list # 无 TTY 时自动批准 shell 钩子

4 · 皮肤与外观

官方文档 · Skins · 仓库 hermes_cli/skin_engine.py

皮肤是纯数据（一个 YAML），一份文件同时给 CLI、TUI、桌面端换色。引擎在 hermes_cli/skin_engine.py，网关会把当前皮肤推给所有界面——所以改完大约一秒内所有界面一起重绘。

换皮肤 / 改一个颜色

hermes skin list # 列出可用皮肤 hermes skin use 皮肤名 # 切换 hermes skin set 键 "#00FFFF" # 只改当前皮肤的一个键（其他都不动） hermes config set display.skin 皮肤名 # 等价的配置写入方式 # 自定义皮肤文件放在：<HERMES_HOME>/skins/<名字>.yaml # 会话内临时换：/skin 名字
两个必须避开的坑
  • 只想改一个颜色，就用 hermes skin set，它会就地改「当前生效的那份皮肤」。不要从 default 派生新皮肤去改一个色——那会丢掉当前整套调色板（包括背景色变成黑的）。
  • 别手改 config.yaml 来启用皮肤，用 hermes config set display.skin。一个多余缩进能让整个网关（包括斜杠命令）报废。

隐藏用法清单

这一节汇总「--help 里查不到、但代码里确实存在」的用法。每一条都标注了它的性质：兼容保留（接受但无效果）、内部用（Hermes 自己调）、无提示可用（你能用，只是没人告诉你）、代码先行（仓库有、当前安装的版本还没有）。

1 · 隐藏的命令行开关

开关性质说明
hermes -p 名 / --profile 名无提示可用在 argparse 之前被摘掉，早于任何模块导入就把 HERMES_HOME 改写掉。所以它必须放在子命令前面
hermes --config 路径无提示可用指定配置文件。只出现在更新器的「保留参数」表里，不在主帮助中

gateway install --elevated-handoff内部用提权交接的内部标记

2 · 提示符里的输入前缀（最实用的一批）

你输入的会发生什么
!命令 shell 直通：直接在会话当前目录执行，消耗 0 个 token，而且不进对话历史（不产生任何 user / assistant / tool 消息）。它仍然走终端工具的审批闸门。
只敲一个 ! 会打印用法提示；连打两个 !! 得到字面量 !。网关 / cron / API 会话里禁用——这是 CLI 专有能力
/ 开头 被当成斜杠命令，但有例外规则：只有当第一个词里不再含 / 时才算命令。所以 /Users/me/x.md 是路径，不是命令
以 /、~、./、../、file://、C:\、C:/ 开头的路径 文件拖入 / 路径直贴：会被解析并附加。图片自动作为图片附件；其他文件包成 [User attached file: ...]
粘贴一大段文本 超过阈值（默认 5 行，或 2000 字符）的粘贴会被折叠成 [Pasted text #N: M lines → <路径>] 的占位符，发送前再展开回真实内容。所以你在输入框里看到一行占位符是正常的
行尾的 \ 续行：这一行不发送，接着写下一行
裸 /resume 之后直接敲数字 选中那个会话——这个数字永远不会被发给模型
任何卡在终端里的失控输入 输入预处理会先剥掉泄漏的 bracketed-paste 包裹符、CPR 转义和鼠标上报转义，再判断你要干什么
! 是这把工具箱里最被低估的一个

「cd 过去看一眼」「git status」「ls -la」这类动作，用 !命令 做，不进对话、不花 token、不污染上下文。它走的是同一套审批闸门，所以该拦的还是会拦。

4 · 三种「单发」的真正差别

hermes -zhermes chat -qhermes chat -Q
走哪条代码路径完全绕过 cli.py，走独立的 oneshot 实现走 CLI，但是「种子」模式走 CLI 的 quiet 单发路径
TTY 上的行为始终单发在真 TTY 上会变成一个交互式会话，把这句话当作第一轮提交；非 TTY、或加 --oneshot / -Q 才单发退出单发退出
stdout 干净度只有最终回答文本（无横幅、无转圈、无工具预览、无 session_id 行）较干净只打印最终回复；会话信息与错误走 stderr
审批自动放行：它内部会设 HERMES_YOLO_MODE=1 和 HERMES_ACCEPT_HOOKS=1（本来就是非交互的）不自动放行；改走确定性的 approvals.single_query_mode 路径，不等 TTY同左
退出码0 完成 · 130 被 SIGINT 中断 · 2 失败/部分完成/迭代预算耗尽 · 1 agent 失败或完成了但没产出文本0 完成 · 130 中断 · 1 失败/部分/压根没跑同左
特殊退出码—在 kanban worker 里（环境里有 HERMES_KANBAN_TASK）：75 = 限流，任务重新排队且不计失败；78 = 供应商终态错误，直接 block 这张卡

-z 的 --usage-file 报告（失败也会写）里包含这些键：estimated_cost_usd、cost_status、cost_source、input_tokens、output_tokens、cache_read_tokens、cache_write_tokens、reasoning_tokens、total_tokens、api_calls、model、provider、session_id、completed、partial、interrupted、turn_exit_reason、service_tier，失败时还有 failed 与 failure；另外 auxiliary{…} 单独统计侧路模型的开销（含 by_task 分解），以及把两者相加的 total_including_auxiliary{…}。

一个真实的坑

在真 TTY 上跑 hermes chat -q "…"，它不会退出——它会开一个交互会话，把那句话当成第一轮。脚本里请用 hermes -z，或显式加 --oneshot / -Q。

事实说明

8 · webhook 的隐藏参数

hermes webhook subscribe 带的开关远比 --help 显示的多，这几个决定了它能怎么用：

参数作用
--prompt提示词模板，用 {点.号.路径} 引用 payload 字段
--events只接受哪些事件类型（逗号分隔）
--secretHMAC 密钥；不填自动生成 32 字节 URL-safe 的
--deliver / --deliver-chat-id投递到哪（默认 log；也可 telegram、discord、slack、github_comment 或任何已注册平台），以及跨平台的目标聊天 ID
--deliver-only跳过 agent，把渲染后的提示词直接当消息推出去（必须给真实 --deliver 目标，与 --cron-job 互斥）
--cron-job不新开 agent 运行，而是按 ID / 名字触发一个已有的 cron 作业，渲染后的提示词作为这次的临时上下文
--script过滤/转换脚本（放在 ~/.hermes/scripts/，payload 从 stdin 进）；stdout 为空、输出 [SILENT]、或非零退出 = 忽略这次 webhook
--mirror-to-session除了投递，还把消息写进目标聊天的会话里
--route-profile绑定到多路复用里的某个 profile：只有 POST 到 /p/<profile>/webhooks/<名字> 才被接受。改这个会轮换密钥
两个「防扩权」设计
  • 每条路由有 toolsets 覆盖项，但只能通过配置文件或手改 JSON 设置——hermes webhook subscribe 给不了。也就是说 agent 自己建的订阅，没法给自己扩权。
  • INSECURE_NO_AUTH 能跳过密钥校验，但只在回环地址上生效。

HTTP 面：GET /health、POST /webhooks/{路由名}、POST /p/{profile}/webhooks/{路由名}，默认端口 8644。请求会按 X-GitHub-Delivery / svix-id / webhook-id / X-Request-ID 做 1 小时幂等去重，agent 运行是异步起的，接口立刻返回 202 accepted。
