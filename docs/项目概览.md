## 一、它解决什么问题

Hermes Agent 是 Nous Research 的个人 AI 智能体（`pyproject.toml:8` 自述为 "self-improving AI agent"）。
它要解决的不是"再写一个聊天机器人"，而是把同**一个 agent 内核**同时跑在 CLI、~20 个消息平台
（Telegram/Discord/Slack/微信/飞书…）、TUI、以及 Electron 桌面端上，并且让它**跨会话自我改进**。

具体承诺（`README.md` 的六条）：

- 真实终端界面 + 斜杠命令 + 中断重定向 + 流式工具输出
- 单一 gateway 进程同时接所有消息平台，跨平台会话连续
- 闭环学习：从经验里创建技能、使用中自我改进、记忆用户、FTS5 检索自己的历史会话
- 内置 cron 调度，结果投递到任意平台
- 子智能体并行 + 后台任务
- 七种终端后端（local/Docker/SSH/Singularity/Modal/Daytona/Vercel），可跑在 5 美元 VPS 上

架构上有两个"宪法级"约束，理解了这个项目的一切设计才有意义：

1. **按会话的 prompt caching 不可破坏。**
   系统提示在一次会话生命周期内必须字节稳定；唯一允许的上下文改写是压缩。
   任何想中途注入的东西只能走 user 消息或 tool result。
   这是它反直觉之处——所以"改系统提示让功能生效"的直觉做法在这里是 bug。

2. **内核是一条窄腰，能力长在边缘。**
   每个模型工具在每次 API 调用都会发给模型，所以新增**核心**工具的门槛极高。
   新能力应该以 CLI 命令 + skill、plugin、或 service-gated tool 的形式出现
   （根 `AGENTS.md` 的 "Footprint Ladder"）。

## 三、代码组织方式（本项目最独特的部分）

### 1. 门面 + 兄弟文件（facade + siblings）——全局统一的架构模式

每个曾经的"上帝文件"都拆成：

- `<stem>.py` **门面**：只放公开入口和别的包会 import 的名字
- `<stem>_<topic>.py` **兄弟文件**：一个文件管一个主题

实例：

```
run_agent.py       → agent/turn_*.py（回合各阶段）、client_lifecycle.py、compression_facade.py …
cli.py             → hermes_cli/cli_*_mixin.py（18 个 mixin）
hermes_state.py    → hermes_state_messages.py / _sessions.py / _schema.py / _search.py …（37 个）
gateway/run.py     → gateway/run_startup.py / run_turn.py / run_busy.py / run_shutdown.py …
tools/mcp_tool.py  → mcp_tool_config / _discovery / _transport / _registration …
```

**关键规则**：兄弟文件在**函数内部**延迟 import 门面（避免模块级循环依赖），
所以"门面就是打补丁的缝"——测试和 monkeypatch 都打在门面上。
按主题找代码用 `grep -rn "def name" <dir>/<stem>_*.py`，不要通读门面。

### 2. AGENTS.md 是真正的契约

根 `AGENTS.md` 是路由表（工作目录 → 该读哪个 AGENTS.md），加上一批跨领域铁律。
每个领域目录还有自己的 `AGENTS.md`，里面的规则不是建议而是硬约束，例如：

- `tools/AGENTS.md`：工具 handler 必须返回 JSON 字符串
- `gateway/AGENTS.md`：两个消息守卫都必须让审批命令穿透
- `skills/AGENTS.md`：技能 `description` ≤ 60 字符，由测试强制

根文件本身有 12k 字符上限，整条根→叶链 30k，所以长文都外链到 `website/docs/developer-guide/`。

### 3. 注册表驱动的工具系统（不是 if/elif 阶梯）

`tools/registry.py` 零依赖，被每个工具文件 import；`tools/*.py` 在模块顶层调
`registry.register(...)`（实测 62 处）。

`discover_builtin_tools()` 用 AST 静态扫描"哪个文件顶层调了 register"，实现零手工导入清单。
工具是包时只扫 `tools/<pkg>/tool.py`。

### 4. 显式 profile 作用域

一个进程服务多个 profile（多实例）。规则：所有在"回合之外"运行的代码
（启动探测、驱逐、定时器、延迟回调、RPC、线程跳转、子进程）都必须**显式绑定所属 profile 的 scope**——
因为 `os.environ`、模块全局、import 期取值拿到的都是启动 profile 的值，不绑定就是静默的默认 profile 泄漏。
这是这个项目里出现频率最高的 bug 类型，相关规则占 `gateway/AGENTS.md` 的一大半。

### 5. 尺寸与复杂度棘轮

`scripts/code_health/config.py` 按单元卡：新函数圈复杂度 ≤ 20、≤ 300 行、嵌套 ≤ 6；文件 ≤ 2000 行。
已经超标的单元只能降不能升。`python scripts/check` 跑 CI 全部阻断性 lint。

### 6. 依赖治理

- 直接依赖全部 `==X.Y.Z` 精确锁（理由写在 `pyproject.toml:20-39`，源于一次 PyPI 投毒事件）
- 改 `pyproject.toml` 必须 `hermes pm lock` 并提交 `uv.lock`
- 绝不裸 pip/uv 改环境
- `.env` 只放密钥，行为配置一律进 `config.yaml`

### 7. 测试约定

- 永远 `scripts/run_tests.sh`，不用裸 `pytest`
- 断言**行为契约**而非快照/计数（禁止 change-detector 测试）
- 平台相关行为用 `@pytest.mark.platforms(...)` 真机测，不伪造 `sys.platform`
- 测试绝不写 `~/.hermes/`

### 工具"注册 ≠ 暴露"

```
tools/*.py 顶层 registry.register()（62 处，import 时执行）
    → tools/registry.py:96   discover_builtin_tools()   AST 扫描
    → model_tools.py:214     get_tool_definitions()
    → model_tools.py:502     _compute_tool_definitions()
    → model_tools.py:315     _select_tool_names()
          读 toolsets.py:74 TOOLSETS（每个命名工具组）
            + toolsets.py:11 _HERMES_CORE_TOOLS
```

**关键**：注册只是让 schema 可用；**只有被某个 toolset 收进去，工具才会发给模型**。
所以新加核心工具必须同时改 `tools/your_tool.py` 和 `toolsets.py` 两处。
可用性判定由 registry 的 `check_fn` 负责，结果按 `hermes_home_key()` 做 TTL 缓存
（一个进程服务多 profile，不能按进程缓存）。

## 五、实操建议

- **找功能实现**：先定位领域目录 → 读该目录的 `AGENTS.md` → 用
  `grep -rn "def X" <dir>/<stem>_*.py` 按主题找兄弟文件。
  **不要通读门面文件**，门面里通常只剩入口和 re-export。
- **改任何东西之前**先确认是否触碰两条不变量：
  prompt caching（别改历史消息 / 中途换工具集 / 重建系统提示）和
  profile scope（回合外的代码必须显式绑定 profile）。
- **加能力**按 Footprint Ladder 从高到低选：
  扩展现有代码 → CLI 命令 + skill → service-gated tool → plugin →
  catalog 里的 MCP server → 最后才是新核心工具。
- **验证命令**：
  - `python scripts/check` —— CI 全部阻断性 lint（含 code health ratchet）
  - `scripts/run_tests.sh` —— 测试（永远不要用裸 `pytest`）
  - `npm run check` —— TS 侧
